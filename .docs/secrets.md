# Безопасность секретов конфигурации

## Кратко

В `application.yml` заданы значения по умолчанию для двух критичных секретов:

- `JWT_SECRET` — ключ подписи JWT.
- `MAIL_ENCRYPTION_KEY` — ключ шифрования почтовых настроек.

Эти значения предназначены только для локальной разработки и тестов. В production секреты следует передавать через переменные окружения или специализированный менеджер секретов. Не используйте в production значения по умолчанию из репозитория.

Если оставить известные значения в production, человек с доступом к репозиторию сможет:

- подделать JWT и выдать себя за пользователя с любой ролью, включая администратора;
- расшифровать почтовые настройки из базы данных, если получит её копию.

## Почему нельзя использовать значения по умолчанию в production

### JWT secret (`JWT_SECRET`)

Ключ используется для подписи токенов доступа. Зная его, можно создать валидный JWT с произвольными ролью и `sub`, обойдя аутентификацию.

Значение по умолчанию хранится в Git. Даже приватный репозиторий доступен разработчикам, подрядчикам, CI-системам и может копироваться в резервные копии. После смены ключа ранее выданные токены перестанут проходить проверку.

### Ключ шифрования почты (`MAIL_ENCRYPTION_KEY`)

Ключ AES-GCM шифрует поля `email`, `password` и `notification_recipient` в таблице `mail_config`. Если ключ известен и получена копия базы данных, почтовые значения можно расшифровать.

В таком случае пароль приложения может быть использован для доступа к почтовому ящику или отправки писем от его имени. Хранение ключа рядом с приложением и зашифрованными данными существенно снижает пользу шифрования.

## Как передавать секреты

### Переменные окружения

Spring Boot подставляет переменные окружения в плейсхолдеры конфигурации. В production следует убрать значения по умолчанию:

```yaml
security:
  jwt:
    secret: ${JWT_SECRET}
  mail:
    encryption-key: ${MAIL_ENCRYPTION_KEY}
```

Если обязательная переменная не задана, приложение не запустится. Это безопаснее, чем незаметно запуститься с известным ключом.

Переменные можно задавать в:

- `systemd` unit-файле (`Environment=`);
- Docker Compose или `docker run`;
- Kubernetes Secret;
- CI/CD secrets или защищённых переменных pipeline.

### Docker Compose

```yaml
services:
  backend:
    image: your-app:latest
    environment:
      JWT_SECRET: ${JWT_SECRET}
      MAIL_ENCRYPTION_KEY: ${MAIL_ENCRYPTION_KEY}
```

Значения можно хранить в `.env` на сервере, но этот файл не следует коммитить.

### Kubernetes

```yaml
env:
  - name: JWT_SECRET
    valueFrom:
      secretKeyRef:
        name: app-secrets
        key: jwt-secret
  - name: MAIL_ENCRYPTION_KEY
    valueFrom:
      secretKeyRef:
        name: app-secrets
        key: mail-encryption-key
```

### Менеджер секретов

Для production предпочтительно использовать специализированное хранилище, например:

- HashiCorp Vault;
- AWS Secrets Manager;
- Google Secret Manager;
- Azure Key Vault.

Spring Boot можно подключить к таким системам через соответствующие интеграции. Секреты тогда выдаются приложению при запуске или во время работы.

## Генерация ключей

Для обоих ключей можно использовать:

```bash
openssl rand -base64 32
```

- Для HS256 значение `JWT_SECRET` должно содержать не менее 32 байт ключевого материала.
- `MAIL_ENCRYPTION_KEY` должен декодироваться из Base64 ровно в 32 байта для AES-256.
- Используйте разные значения для JWT и шифрования почты.

## Чек-лист перед production-деплоем

- [ ] Удалить значения по умолчанию из плейсхолдеров `JWT_SECRET` и `MAIL_ENCRYPTION_KEY` в `application.yml`.
- [ ] Задать обе переменные в production-окружении или настроить менеджер секретов.
- [ ] Убедиться, что JWT-ключ и ключ шифрования почты различаются.
- [ ] Сгенерировать случайные ключи, а не придумывать их вручную.
- [ ] Проверить, что секреты не попадают в логи.
- [ ] Убедиться, что `.env`, `application-local.yml` и `application-local.yaml` не коммитятся.
- [ ] Оставить в `application-test.yml` только тестовые ключи и комментарий `# test-only keys, do not reuse in prod`.
- [ ] Если ключ когда-либо попадал в Git, считать его скомпрометированным и заменить.

## Действия при утечке ключа

### Утёк `JWT_SECRET`

1. Сгенерировать новый ключ.
2. Заменить `JWT_SECRET` в окружении.
3. Перезапустить приложение.

Ранее выданные токены станут недействительными; пользователям потребуется войти заново.

### Утёк `MAIL_ENCRYPTION_KEY`

Зашифрованные значения в базе данных нельзя расшифровать новым ключом. До его замены нужно выполнить ротацию:

1. Расшифровать все значения `mail_config` старым ключом.
2. Зашифровать их новым ключом.
3. Сохранить новые шифротексты в базе данных.
4. Заменить `MAIL_ENCRYPTION_KEY` в окружении.
5. Перезапустить приложение и проверить доступность настроек.

Для одного почтового ящика в приложении обычно достаточно обработать одну запись. При нескольких записях нужно обработать их все.

## Значения по умолчанию в репозитории

Значения по умолчанию упрощают запуск тестового проекта и локальную разработку. Это компромисс, а не production-настройка: перед production-деплоем значения нужно удалить, а секреты передать из защищённого источника.

Комментарии `TODO` рядом с секретами в `application.yml` служат напоминанием и не заменяют production-чек-лист.

## Доступ к запущенному приложению с других устройств по сети

Приложение работает в браузере, поэтому подключиться можно с компьютера, ноутбука,
планшета или смартфона с актуальным Chrome, Firefox, Edge или Safari. Устройство
должно быть подключено к той же локальной сети, что и компьютер или сервер с
приложением. Войдите под своей учётной записью Service Desk.

### Подключение в локальной сети

1. Запустите приложение на компьютере-хосте: `docker compose up -d`.
2. Узнайте его локальный IPv4-адрес. В Windows выполните `ipconfig` и найдите
   «IPv4-адрес» активного сетевого подключения; в Linux — `hostname -I`.
3. На другом устройстве откройте в браузере `https://АДРЕС_ХОСТА:8080`,
   например `https://192.168.1.25:8080`.

Compose публикует HTTPS-порт `8080` на сетевых интерфейсах хоста. Если подключение
не удаётся, разрешите входящие TCP-подключения к порту `8080` в брандмауэре хоста
для частной/домашней сети. Например, в PowerShell от имени администратора:

```powershell
New-NetFirewallRule -DisplayName "Service Desk HTTPS" -Direction Inbound -Protocol TCP -LocalPort 8080 -Action Allow -Profile Private
```

Для Linux с UFW разрешите порт только для своей локальной подсети, заменив пример
`192.168.1.0/24` на адрес и маску своей сети:

```bash
sudo ufw allow from 192.168.1.0/24 to any port 8080 proto tcp
```

При открытии по IP браузер может предупредить о сертификате: текущий сертификат
самоподписанный и выпущен для `localhost`, а не для локального IP-адреса.
Для использования без предупреждений настройте сертификат, доверенный устройствами
и выпущенный для имени хоста, по которому открывается приложение.

### Доступ из глобальной сети

Не открывайте порт приложения в интернет простым пробросом порта на роутере:
текущая конфигурация и сертификат предназначены для локального запуска. Для
внешнего доступа разверните приложение на защищённом сервере, настройте доменное
имя и HTTPS-сертификат от доверенного центра сертификации, замените секреты по
инструкции выше и ограничьте доступ брандмауэром или VPN.
